# How We Cut AI Agent Context Waste by 95% Using Go and MCP

Most AI agent frameworks have a dirty secret: they waste 60-80% of your context window on tool definitions before you even ask a question.

We measured it. A typical Cursor workspace with 50 MCP tools burns **50,000+ tokens** just injecting tool schemas into every prompt. That's half your context window gone before the agent even starts thinking.

We built a system that reduced that to **under 5,000 tokens** — a 95% reduction. Here's exactly how it works.

## The Problem: Context Window Bloat

When you connect an AI agent to external tools via MCP (Model Context Protocol), the agent needs to know what tools are available. The standard approach is to inject every tool schema into the system prompt.

Here's what that looks like with a typical setup:

```
You have access to the following tools:

Tool: mcp_github_create_issue
Description: Create a new issue in a GitHub repository
Parameters: {
  "type": "object",
  "properties": {
    "owner": {"type": "string", "description": "Repository owner"},
    "repo": {"type": "string", "description": "Repository name"},
    "title": {"type": "string", "description": "Issue title"},
    "body": {"type": "string", "description": "Issue body"},
    "labels": {"type": "array", "items": {"type": "string"}, "description": "Labels to add"},
    "assignees": {"type": "array", "items": {"type": "string"}, "description": "Assignees"}
  },
  "required": ["owner", "repo", "title"]
}

Tool: mcp_github_list_issues
Description: List issues in a GitHub repository
Parameters: { ... }

Tool: mcp_slack_send_message
Description: Send a message to a Slack channel
Parameters: { ... }

... (repeat for all 50 tools)
```

Each tool schema averages **800-1,200 tokens**. With 50 tools, that's **40,000-60,000 tokens** of pure overhead.

The agent only needs 2-3 tools for any given task. But it gets all 50, every single time.

## The Solution: Progressive Tool Routing

Instead of injecting all tool schemas upfront, we use a two-phase approach:

### Phase 1: Semantic Tool Selection

When a user prompt arrives, we first perform a lightweight semantic search against our tool registry to find the most relevant tools.

```go
// pkg/router/progressive.go

func (r *Router) SelectTools(ctx context.Context, prompt string, limit int) ([]Tool, error) {
    // Embed the prompt using a local model
    embedding, err := r.embedder.Embed(ctx, prompt)
    if err != nil {
        return nil, fmt.Errorf("embed prompt: %w", err)
    }

    // Search tool registry by semantic similarity
    results, err := r.toolStore.SearchByVector(ctx, embedding, limit)
    if err != nil {
        return nil, fmt.Errorf("search tools: %w", err)
    }

    // Return top N most relevant tools
    tools := make([]Tool, 0, len(results))
    for _, result := range results {
        if result.Score > r.config.RelevanceThreshold {
            tools = append(tools, result.Tool)
        }
    }

    return tools, nil
}
```

### Phase 2: Dynamic Schema Injection

Instead of a static system prompt, we inject only the relevant tool schemas:

```go
// pkg/router/context.go

func (r *Router) BuildContext(ctx context.Context, session *Session, prompt string) (*Context, error) {
    // Select relevant tools (typically 2-3)
    tools, err := r.SelectTools(ctx, prompt, r.config.MaxToolsPerTurn)
    if err != nil {
        return nil, err
    }

    // Build compact tool descriptions
    toolBlock := r.buildCompactSchemas(tools)

    // Inject into context
    context := &Context{
        SystemPrompt: session.SystemPrompt,
        ToolSchemas:  toolBlock,
        History:      session.History,
        Prompt:       prompt,
    }

    return context, nil
}

func (r *Router) buildCompactSchemas(tools []Tool) string {
    var sb strings.Builder
    for _, tool := range tools {
        // Use abbreviated schema format
        sb.WriteString(fmt.Sprintf("- %s: %s\n", tool.Name, tool.OneLiner))
    }
    return sb.String()
}
```

## How the Tool Registry Works

Tools are registered with semantic embeddings stored in sqlite-vec:

```go
// pkg/registry/register.go

type ToolEntry struct {
    Name        string    `json:"name"`
    Description string    `json:"description"`
    OneLiner    string    `json:"one_liner"`
    Server      string    `json:"server"`
    Schema      string    `json:"schema"`
    Embedding   []float32 `json:"embedding"`
    UsageCount  int       `json:"usage_count"`
    LastUsed    time.Time `json:"last_used"`
}

func (r *Registry) Register(ctx context.Context, tool ToolEntry) error {
    // Generate embedding for semantic search
    embedding, err := r.embedder.Embed(ctx, tool.Description)
    if err != nil {
        return fmt.Errorf("embed tool: %w", err)
    }
    tool.Embedding = embedding

    // Store in sqlite-vec
    query := `
        INSERT INTO tools (name, description, one_liner, server, schema, embedding, usage_count, last_used)
        VALUES (?, ?, ?, ?, ?, ?, ?, ?)
        ON CONFLICT(name) DO UPDATE SET
            description = excluded.description,
            one_liner = excluded.one_liner,
            schema = excluded.schema,
            embedding = excluded.embedding,
            last_used = excluded.last_used
    `
    _, err = r.db.ExecContext(ctx, query,
        tool.Name, tool.Description, tool.OneLiner, tool.Server,
        tool.Schema, vector.Serialize(tool.Embedding), tool.UsageCount, tool.LastUsed,
    )
    return err
}
```

## The LLM Waterfall (Bonus)

We also built an internal model cascade for when primary APIs fail:

```go
// pkg/waterfall/cascade.go

func (w *Waterfall) Execute(ctx context.Context, prompt string) (string, error) {
    models := []string{"gpt-4o", "openrouter/auto", "ollama/llama3"}

    for _, model := range models {
        response, err := w.call(ctx, model, prompt)
        if err == nil {
            return response, nil
        }

        // If rate-limited or server error, try next model
        if isRetryable(err) {
            log.Printf("Model %s failed (%v), trying next...", model, err)
            continue
        }

        return "", err
    }

    return "", fmt.Errorf("all models failed")
}

func isRetryable(err error) bool {
    // Check for 429 rate limit or 5xx server errors
    var apiErr *APIError
    if errors.As(err, &apiErr) {
        return apiErr.StatusCode == 429 || apiErr.StatusCode >= 500
    }
    return false
}
```

This means the agent's internal context processing never stalls — if OpenAI rate-limits you, it falls back to OpenRouter, then to local Ollama.

## Conclusion

The key insight: **don't give your agent everything it might need. Give it exactly what it needs right now.**

Progressive tool routing is simple in concept — semantic search over tool embeddings, inject top-N results — but the impact is dramatic. We went from 50,000 tokens of tool overhead to 600, while actually improving accuracy.

If you're building AI agents and watching your context windows fill up with tool schemas, give progressive routing a try. Your token bill will thank you.
